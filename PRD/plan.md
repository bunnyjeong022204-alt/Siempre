# PLAN — 어떤 순서로 실행할지

## 1. 역할

| 이름 | 맡은 것 |
| --- | --- |
| 변희정 | PM, 기술 스택·DB 결정, 화면 시안 확정, 일정 관리, 완료 판단, **광고 기획·대본 확정** |
| 권희수 | 홈페이지 전체 흐름. 구독·결제·대화·크레딧의 프론트엔드와 백엔드 |
| 김형민 | 회원가입·로그인의 프론트엔드와 백엔드 |
| _(정할 것)_ | 광고 영상 제작(AI 영상 생성·편집), 녹음 진행 |

담당은 "먼저 책임지고 만드는 사람"이다. 막히는 부분은 다 같이 돕는다.
광고 녹음은 배역을 셋이 나눠 맡는다(7장).

## 3. 제품 단계

| 단계 | 할 일 | 담당 | 끝나면 |
| --- | --- | --- | --- |
| 0. 준비 | 기술 스택·DB 결정, 공통 코드(`backend/shared`) 올리기, 화면 시안 확정 | PM | 서버가 뜨고 빈 화면이 열린다 |
| 1. 가입·로그인 | 가입·로그인 화면 + auth API | 김형민 | 가입하고 로그인된다 |
| 2. 구독 | 장바구니·결제 화면 + subscription API | 권희수 | 결제하면 구독이 저장된다 |
| 3. 대화·크레딧 | 대화·크레딧 화면 + chat·credits API (처음엔 가짜 답변) | 권희수 | 가짜 답변으로 전체 흐름이 돈다 |
| 4. 실제 AI 연결 | 가짜 답변을 실제 공급사 호출로 바꾸기, API 키 연결, 라우팅 다듬기 | 모두 | 실제 AI가 답한다 |
| 5. 합치고 점검·배포 | 전체 흐름 테스트, SPEC 완료 기준 확인, 버그 수정, 배포 | 모두 | MVP 완료, 접속 주소가 생긴다 |

### 0단계 · 준비 (PM)
- 언어·프레임워크, DB를 정해 [`backend/shared/README.md`](../../backend/shared/README.md) 1장에 적는다.
- 서버 시작 파일, DB 연결, 오류 응답 형식을 `backend/shared/`에 올린다.
- Figma 화면 시안을 확정하고 프론트엔드 담당 두 사람에게 공유한다.

### 1단계 · 가입·로그인 (김형민)
- 가입·로그인 화면을 만든다.
- [`backend/auth/README.md`](../../backend/auth/README.md)의 API를 만든다.
- **"로그인한 사용자 확인" 함수(`currentUser`, `requireUser`)를 가장 먼저 올려** 권희수가 바로 쓸 수 있게 한다.

### 2단계 · 구독 (권희수)
- 홈 → 구독 선택 → 데모 결제 화면 흐름을 만든다.
- [`backend/subscription/README.md`](../../backend/subscription/README.md)의 API를 만든다.
- 김형민의 함수가 오기 전에는 가짜 로그인 함수(항상 테스트 사용자)로 작업한다.

### 3단계 · 대화·크레딧 (권희수)
- 대화·크레딧 화면을 만든다.
- [`backend/chat/README.md`](../../backend/chat/README.md), [`backend/credits/README.md`](../../backend/credits/README.md)의 API를 만든다.
- AI 호출은 가짜 답변으로 먼저 만들어, API 키 없이도 화면을 확인할 수 있게 한다.
- 크레딧은 결제한 요일을 기준으로 매주 채운다 (PRD 4-1).

### 4단계 · 실제 AI 연결 (모두)
- 공급사별 API 키를 발급받아 서버 `.env`에 넣는다. 깃헙에는 올리지 않는다.
- 가짜 답변 자리에 실제 공급사 호출을 넣는다.
- 여러 요청을 직접 보내 보며 분류가 맞는지, 차감 크레딧이 PRD 4-2와 같은지 확인하고 규칙을 다듬는다.

### 5단계 · 합치고 점검·배포 (모두)
- 가짜 함수를 모두 진짜로 바꾼다.
- 새 계정으로 SPEC 1장의 흐름을 처음부터 끝까지 진행한다.
- SPEC 2·3장 체크리스트를 확인하고, 남은 버그를 고친다.
- 배포하고, 배포 주소로 같은 흐름을 한 번 더 진행한다. 이 화면을 광고 마지막 장면과 발표 시연에 쓴다.

## 4. 광고 기획

### 4-1. 목표
- 발표에서 Siempre가 **무엇을 해 주는 서비스인지 24초 안에** 전달한다.
- 보고 나서 기억할 것 하나: **"고르는 건 Siempre가 한다"** (알맞은 AI가 자동으로).

### 4-2. 누구에게
- PRD 2-3 핵심 사용자: 작업마다 AI를 바꿔 쓰는 직장인·마케터·1인 크리에이터.
- 광고 속 상황은 직장인(기획안 작성)으로 잡는다. 가장 많은 사람이 바로 공감하는 장면이라서.

### 4-3. 콘셉트
AI 하나로 다 하다가 험담을 듣던 주인공이 Siempre로 뒤집는다. 알고 보니 팀장도, 사무실 전체도 이미 Siempre를 쓰고 있었다.

- 마지막 문장: **"너 빼고 다 쓰고 있는, Siempre."**
- 대본 전문: `Siempre 광고 대본 초안.md` (브랜치 `AD-(1522sec)`)

### 4-4. 흐름

| 구간 | 내용 | 전달할 것 |
| --- | --- | --- |
| 0–5초 | 탕비실 험담, 주인공 손이 멈춤 | 문제: AI 하나로는 티가 난다 |
| 5–11초 | 이름 없는 챗봇이 "알아서 맞춰 주는 AI를 써요" | 전환 |
| 11–14초 | Siempre 대화창, 요청마다 모델 칩이 바뀜 | 핵심 기능: 자동 라우팅 |
| 14–20초 | 팀장 칭찬, 팀장 화면에도 Siempre | 반전 |
| 20–24초 | 사무실 전체 Siempre, 로고 | 브랜드 각인 |

20초 줄임안은 대본 문서를 따른다.

### 4-5. 만드는 방법
- 영상: AI로 장면 생성 (HyperFrames). 말하는 장면은 뒷모습·옆모습·어깨 너머로 잡아 입 모양 문제를 피한다.
- 목소리: 팀원이 직접 녹음. 챗봇 대사는 녹음하지 않고 말풍선 타이핑으로 보여 준다.
- Siempre 화면: 가능하면 **배포한 실제 화면을 녹화**해서 넣는다. 안 되면 Figma 시안으로 만든다.
- 로고: 로고 확정 전이면 분홍 배경 + "Siempre" 글자로 임시 처리한다.

| A. 콘셉트 | 목표·대상·한 줄 콘셉트 정하기 | PM | 4-1~4-3이 정해진다 |
| B. 대본 | 대본 초안, 20초 줄임안 | PM | 대본 문서가 올라간다 |

| 배역 | 대사 | 맡는 사람 |
| --- | --- | --- |
| 동료 A | 험담 첫 대사 | 1번 |
| 동료 B · 이 팀장 | "그래서 이 팀장이…", "오, 이번 거 좋은데?" | 2번 |
| 주인공 · 내레이션 | 억울한 대사, "AI한테 맡긴다고?", "감사합니다", 내레이션 두 줄 | 3번 |

1·2·3번에 누구를 넣을지는 5교시 전에 정한다.

### 4-8. 광고 체크리스트 (최종본 전에 확인)
- [ ] 실제 경쟁 서비스 이름("챗지피티" 등)이 대사·화면에 없다. 주인공 챗봇은 이름 없는 창이다.
- [ ] 실제 회사 로고를 AI로 그리지 않았다. 모델은 색 원 + 이니셜 + 이름 글자로 표시했다.
- [ ] "AI 티 안 나요" 같은 결과 보장 문구가 없다. 메시지는 "알맞은 AI가 자동으로"다.
- [ ] Siempre 화면 속 모델 칩이 **PRD 3-1 입점 AI와 같다** (4-9 참고).
- [ ] MVP에 없는 기능(음성 등)은 화면 속 버튼으로 넣지 않았다. 필요하면 "곧 출시" 칩으로만 보여 준다.
- [ ] 반전 장면(팀장 화면)의 칩과 답변 문장이 1초 이상 멈춰 읽힌다.
- [ ] 길이가 24초(또는 20초) 안이다.
- [ ] 발표 화면에서 소리가 잘 나오는지 미리 틀어 봤다.

### 4-9. 정할 것
- **광고 속 모델 이름**: 대본은 Claude·Qwen·Nano Banana(PRD03 기준)인데, 지금 코드가 따르는 PRD02는 GPT·Qwen·Mistral이다. 어느 PRD를 기준으로 할지 정하고 대본의 칩을 맞춘다.
- **"음성 생성 곧 출시" 칩**: 음성 기능이 로드맵에 있는지 확인하고, 없으면 뺀다.
- **광고 제작 담당**과 **녹음 배역 1·2·3번**.

## 5. 진행 방식

- 제품 2·3단계는 1단계와 **동시에** 시작한다.
- 1단계가 끝나면 김형민과 권희수가 함께 가짜 로그인 함수를 진짜로 바꾸고 전체 흐름에 연결한다.
- 광고는 제품 개발과 **따로 나란히** 진행한다. 제품 담당이 광고 때문에 개발을 멈추지 않도록, 녹음처럼 짧은 일만 함께한다.
- 단계마다 PR 하나씩 올리고, main에 합치기 전에 다른 사람이 확인한다.
- 브랜치 이름: `frontend/<화면>-<작업>`, `backend/<파트>-<작업>`, `ad/<작업>` (예: `frontend/signup-form`, `backend/chat-routing`, `ad/storyboard`).
- 광고 대본·스토리보드는 `docs/ad/`에 올리고, 영상 파일은 용량이 커서 깃헙 대신 공유 드라이브에 둔다.
- 기획과 코드가 다르면 PRD를 따르고, 애매하면 PRD 9장 "열린 질문"에 적는다.
